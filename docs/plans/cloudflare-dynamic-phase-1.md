# Phase 1 数据读取层实施记录

当前状态为实施中。第一批交付公开详情和最新收录查询，第二批增加成员数/标签排序投影、首页运营读取和版本化缓存协议。推广优先排序、数字页码映射、排行与 R2 一致性继续验收。

第一批对应 PR #24（P1-2），第二批对应依赖 #24 的 PR #23（P1-4 及前置基础）。
后续每个可验收交付节点另开 PR，合并顺序为 #21 → #22 → #24 → #23。

## 已实现的读取边界

- `getPublicEntry()` 按规范化 username 查询，使用唯一索引，强制 approved，单条详情通过左连接读取统计，标签按 entry_id 定向读取。
- `listPublicLatest()` 使用 listed_at 降序、username 升序的稳定游标，每次最多返回 60 条，额外读取 1 条判定下一页。
- DTO 明确列出公开字段。时间字段使用数据库毫秒值，头像使用版本值，Phase 2 负责转换成现有公开页面契约。
- 原最新列表支持 kind/categoryId。新增 `listPublicDirectory()` 支持全站、类型、分类和标签范围的成员数/最新排序。
- 详情直接读取权威表，目录使用事务内触发器维护的派生排序键，最终 JOIN entries 校验 approved。
- 新增首页固定键计数、分页分类/标签计数、公告/友链设置和有效推广读取。旧版部分设置与默认值合并后校验。

## 第二批投影与验证

- `0023_public_listing.sql` 新建 scope 排序投影，scope 包含全站、类型、分类和条目所属标签。
  两个 `(scope, order, username)` 索引分别支持成员数和最新排序，另有 entry_id 索引用于同步与回填。
- `0024_public_counts.sql` 按 scope 维护计数，并新增推广 ends_at/id 索引。首页统计读取四个固定 scope，
  分类标签计数读取对应计数行。成员数更新只修改排序键，计数保持不变。
- 源表触发器和版本更新在同一个 D1 事务中执行。默认未启用投影，旧调用链继续使用原读取方式。
  未启用时触发器仍执行门禁检查，启用后的额外读写成本按样本预算单独计量。
- `beginPublicProjection()` 显式启用同步，`backfillPublicProjection()` 每批最多处理 100 个源条目，
  进度与投影同批提交，通过 cursor 条件防止并发批次倒退。重复启动保留进度，完成后设置 ready。
- 公开投影读取要求 enabled/ready，并在查询前后检查版本。游标绑定 scope、sort 和 revision，
  数据版本变化时要求重新开始分页。

本地 D1 等价样本验证了 1000 个条目中仅 1 个属于目标标签的场景。

| 指标 | 实测结果 | 范围 |
|---|---:|---|
| 直接关联过滤的成员数基线 rows-read | 1003 | 同一固定样本 |
| 投影成员数/最新查询 rows-read | 均为 4 | 仅业务 SELECT，不包含前后版本校验 |
| 一次有 1 个标签的成员数更新 rows-written | 10 | 启用投影和版本同步后 |
| 实际查询计划 | 命中对应 scope 排序索引，无临时排序 | 捕获真实 SQL 与绑定参数 |

每个已审核条目产生 `3 + 标签数` 条投影记录，另有索引和计数写入成本。以上是本地 workerd 指标，
生产分布、标签数量、并发与 Paid 总预算仍需隔离环境复测。成员数/最新基础排序尚待与现有推广优先规则组合。

## 索引与迁移

新增 `0022_public_latest.sql`，包含三个 approved 部分索引。

| 查询 | 索引 | 依据 |
|---|---|---|
| 全站最新 | entries_public_latest | listed_at DESC、username 覆盖排序 |
| 类型最新 | entries_public_kind_latest | kind 等值后复用稳定排序 |
| 分类最新 | entries_public_category_latest | category_id 等值后复用稳定排序 |

测试使用本地 D1 的 `EXPLAIN QUERY PLAN` 验证对应索引与无临时排序。每个 approved 条目最多增加
三个索引记录，新增/删除及排序键更新产生相应写放大。生产规模的 rows-read/rows-written 和包体/CPU
数据仍需隔离环境测量，生产迁移需单独确认。

0022 只建立索引。0023/0024 的投影使用上述分批 API 回填，尚待补齐运维命令入口和全量一致性审计。
本批资源使用现有 D1。
索引失效时应用可回退到上一版本。需要移除索引时按以下顺序在已授权环境执行。

```sql
DROP INDEX IF EXISTS entries_public_category_latest;
DROP INDEX IF EXISTS entries_public_kind_latest;
DROP INDEX IF EXISTS entries_public_latest;
```

## 缓存协议设计边界

下列协议需要在 Phase 1 后续批次验证，并在 Phase 2 首次切换前验收。

| 结果 | 缓存键维度 | 失效依赖 |
|---|---|---|
| 详情 | schema version、locale、username | 状态、文案、翻译、标签、统计、隐藏规则、R2 内容、推广 |
| 列表 | schema version、locale、kind、分类/标签、sort、page/cursor | 条目新增/状态/排序值、分类标签、推广 |
| 首页/排行 | schema version、locale、榜单类型 | 状态、统计、历史投影、推广、时间窗口 |
| Sitemap/公开 JSON | schema version、分片、locale、数据版本 | 公开状态、URL、更新时间、分类标签 |

候选读取流程为 D1 权威版本/状态校验、版本化缓存命中或定向回源、回填前版本复核。版本更新须与 D1
变更原子提交。R2 内容变更还需解决跨存储写入顺序和失败恢复。缓存键必须覆盖所有依赖，尤其是翻译、
帖子隐藏与推广自然过期。

`readPublicCached()` 已实现上述 D1 数据版本协议，缓存键包含协议版本、内容版本及调用方提供的语言、范围、排序和分页维度。
读取前后各检查一次权威版本，命中后跳过业务 loader。缓存读取、写入或解码失败回退权威读取，
版本不可确认则返回错误。并发写入导致版本变化时拒绝以旧版本发布结果。
`validUntil` 可限制时间相关结果的缓存寿命，当前尚待补齐推广下一次开始/结束时间的完整计算。
R2 写入与 D1 跨存储失败恢复仍待验证，现有 R2 刷新尚未接入新增的媒体失效函数。
启用媒体或推广缓存前需要完成这些依赖测试。

验收分别记录命中与未命中的 D1 请求数、rows-read、CPU、延迟、缓存回填量和写放大。
当前协议每个命中请求仍有两次轻量 D1 版本读取，尚待 Phase 2 在请求内复用校验结果。
多地区缓存通过版本键隔离旧值，实际 Cloudflare Cache/KV adapter、跨地区行为与 CPU 仍需 Workers 环境验证。
