## 实现与不变量

- shared/health.ts：严格证据校验、公开身份与功能结果分离、无原始HTML/token字段、重定向诊断剥离认证信息/查询/fragment、正向识别需200/entity/类型匹配。标签不把账号可识别写成“功能正常”。
- migration 0027_entry_health.sql + schema：两张私有表，只新增不回填旧active/fail_count；证据每条目16槽，来源/状态/槽范围/JSON约束与索引。旧表/旧列保留至阶段四，不从历史隐藏推导新结论。
- db/health.ts：网页观察、人工功能检查、显式身份确认、按页读当前状态和读最近证据。写入不操作entries.status/kind或旧失败字段，不产生通知或发布构建。
- 当前状态及有界证据使用同一D1 batch事务；以SQL条件原子UPSERT保护时间/绑定，省去外部先读后CAS的竞态。每次写入按2个SQL保守预算，实际一次D1 batch调用；返回rowsRead/rowsWritten便于入口接入时计账。官方事务依据：https://developers.cloudflare.com/d1/worker-api/d1-database/#batch 。
- 重复ID、同时间及迟到结果不覆盖新状态；profile/preview归约为同一次观察，不被当成独立来源。相同原因的重复正常诊断按一小时采样，状态仍保留最新成功时间。
- 公开身份和功能分别维护时间，互不覆盖。功能明细单独保留最近一次，避免被16槽环挤出后失去操作范围；仍然只是有时间/范围的历史验证，不证明长期可用。
- identity_review保持到显式人工确认；类型异常立即清除当前功能验证，复核期间拒绝新功能验证。人工确认要求revision匹配，清为unverified而非伪造抓取成功，并建立时间栅栏拒绝复核之前启动的旧任务。
- 当前仅按username/kind绑定，不能证明同名账号未被转让；没有稳定Telegram ID前，不据此自动恢复旧条目。不存在自动隐藏/恢复权限。
- shared/db health-source：profile/preview各自控制，5分钟起步指数退避、本地上限60分钟，Retry-After可超过本地上限；旧结果不能覆盖新退避，CAS拒绝并发旧所有者，损坏状态显式失败不清零。来源退避不等于单条资源失效。

## 验证与限制

- 真实本地D1测试：四种发布状态保持、旧active不回填、重复/迟到/并发、两维隔离、身份变化/人工复核栅栏、证据写入失败整批回滚、16槽上限、旧主体遮蔽、外键清理及来源CAS。
- 规模测量：2092条额外资源+1条样本，读取100条实际health page为300 rows-read/1 SQL，随页大小有界；不是最初估算的200。单次写入按2 SQL预留，写量断言<=8，重复请求0写入。该结果是本地D1测量，不当成生产费用/吞吐结果。
- Node SQLite测试从0000–0026建库并插入旧系统隐藏记录，再应用0027，验证全部旧字段/status保持、health/evidence为空；迁移不伪造历史成功，也不恢复隐藏条目。
- 接口只供后续可信服务端接入：actor/时间/observationId应由认证后服务端生成。此节点没有开放HTTP端点或人工审批入口，不声称已有完整鉴权/审计/UI。2B2必须在审计事务/权限保护下调用人工接口。
