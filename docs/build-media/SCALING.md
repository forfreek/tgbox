## 当前行为与实测基线

每次实际执行静态构建，都会重新读取全部公开条目所需的 JSON，再生成完整快照、页面与 Pagefind 索引。dirty 检查只能跳过无变更的整次构建，不是逐条目增量构建。

R2 S3 读取只改变输入通道，未改变全量构建模式。16 个并发任务限制同时在途请求数量，不限制累计数据量或整个快照的内存占用。`packages/snapshot/src/build-site-data.ts` 将媒体数据汇总到内存，`cli.ts` 最终序列化整个 SiteData。

## 风险与平台边界

- 条目数量增长：N+C 次读取、页面生成数量、索引规模、耗时和直接 R2 GET 操作量随之增长。S3 直读不使用公开域名缓存。
- 单对象增长：帖子或历史 JSON 增大会增加传输、解析、快照内存及序列化成本；本节点没有审计所有写入路径的保留/聚合规则，不能宣称历史无限增长或已有可靠上限。
- 当前工作流 `timeout-minutes: 30`，比 GitHub 平台单 job 的 6 小时上限更早生效。不能通过放宽超时替代容量设计。
- 当前仓库为公开仓库，ubuntu-latest 标准规格在本次核对为 4 CPU、16 GB RAM、14 GB SSD；磁盘还需容纳依赖和构建产物。这些是平台规格，不是应用可用资源保证。
- Workers Free 静态文件上限 20000，Workers Paid 为 100000，单文件上限均为 25 MiB。本次未独立核实账户 Workers 套餐；按 Free 容量预算时，10659 个文件约占 53%。不得按线性比例承诺还能容纳多少条目。
- Workers Paid 和域名 Pro/Super Bot Fight Mode 是不同产品，不能把它们的额度或升级效果混为一谈。

以上平台规格是 2026-11-20 快照，行动前重新核实：[GitHub runner](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)、[Actions 限制](https://docs.github.com/en/actions/reference/limits)、[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)。

## 后续评估顺序与验收要求

1. 先补容量测量：N/C、逻辑请求及重试量、JSON 字节、单对象最大值、峰值 RSS、快照/产物大小、各阶段耗时和最终上传文件数。区分源码已有日志与尚未实现的指标。
2. 核查帖子和历史的写入上限、读取窗口及展示需求，再设计保留、聚合或分页；未经业务确认不得直接删历史。
3. 对照既有动态化计划评估频繁变化内容脱离全站重建的路径；相关资料在其他工作树，先核对各自索引和状态。本记录不代表重新授权整项动态化。
4. 如采用增量缓存，必须定义对象版本/ETag、删除与失效、缺失对象、构建期间变更、缓存丢失及全量重建的正确性。单纯跳过下载不等于增量页面构建。
5. 如采用分批处理，验证是否真正降低峰值内存；如果最后仍汇总整个 SiteData，不能宣称已解决内存增长。
6. 用多规模样本与故障场景验证完整输出、更新后可见性、内存/耗时/文件数预算，再确定报警阈值及实施节点。峰值内存和条目容量尚无压测结论。

本次只登记问题和评估入口，不增加缓存、裁剪数据、修改套餐、调整生产资源或改变构建模式。
