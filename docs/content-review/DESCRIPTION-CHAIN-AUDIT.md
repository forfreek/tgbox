## 第 3 步需要修复的问题

### 1. 源语言依据混用

maintenance.ts:41 优先使用条目的 lang，该值来自标题、简介和最近消息的合并检测。第三语言再按有无汉字回退为 zh/en。俄语被当英语，含汉字的日文被当中文，现有测试明确覆盖该行为。

验收要求为简介文本独立判断来源语言，明确支持语言和无法确认时的处理，覆盖俄、阿、日、中英混排及条目语言与简介语言不同的样本。第三语言需要明确两种目标语言的生成策略。

### 2. 输出接受条件过宽

maintenance.ts:84–90 将非空 translated_text 直接保存。原文中的用户名、网址和联系方式缺少保留校验，目标语言和重复文本也缺少质量门槛。本地模拟将重复的 @wrong_bot 写入成功，线上样本同时存在标识变形。

验收要求为生成前保护标识，生成后核对保留、目标语言、重复和空输出。异常结果进入可重试状态，保留可追踪的原因。模型返回内容按数据处理。

### 3. 旧推理结果可能在原文刷新后写回

translations.ts:57 保存时仅按 entryId 匹配。候选读取后，源简介被刷新，再保存旧结果，可以形成新原文配旧译文。本地按维护任务使用的开始时间戳复现，条目仍会重新排队，但在重试完成前旧译文已经可被导出。

验收要求为写入时比较候选对应的原文身份或版本，原文变化时拒绝过期结果。跳过标记也需遵循相同源身份约束，并覆盖并发和重试场景。

### 4. 种子导入绕过译文失效

seed-sql.ts:32 冲突更新 description 时保留 description_zh、description_en。本地使用实际迁移和 seedEntrySql 重跑，确认新源简介与旧中文译文共存。后续翻译可能重新排队，旧译文仍可在此期间被展示。

验收要求为刷新、新收录、种子重跑等写入入口采用一致的失效规则，并验证无变化重跑的幂等性。

### 5. 失败队列可能阻塞后续条目

maintenance.ts:85–98 的空结果和异常保留原时间戳，translations.ts:49 按旧时间戳、id 取前若干条。前 8 条持续失败时，本地连续两个小时任务均请求同一批 8 条，第 9 条未被请求。

验收要求为记录尝试与延后时间，设置有界重试或隔离机制，后续有效条目能够继续处理，单条失败仍与批次隔离。

### 6. 无关字段更新会重复排队

updateEntryCold 对标题、头像等变化更新 updatedAt，候选查询再将旧翻译时间戳与 updatedAt 比较。本地复现标题单独变化后，相同简介重新入队。分类、标签等使用该时间戳的入口也需要在实现时逐项覆盖。

验收要求为按简介和语言处理规则的变化决定失效，跳过、成功、规则升级和人工修正都能正确处理。

### 7. 人工内容与存量修正需要明确边界

现有后台编辑接口主要处理分类、标签和推广，源简介随 Telegram 刷新。后续编辑简介需要明确来源、人工覆盖、失效和撤回关系。存量已有非空坏译文还需要重新进入处理范围，否则增加输出校验只会影响后续请求。

验收要求为先确定最小人工修正方式，保护人工内容，并为样本及存量修复提供预览、范围限制和回退。具体字段设计留在第 3 步方案。
