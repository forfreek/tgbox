# 收录刷新进度修复

头像 URL 兼容补充节点（2026-11-21）见下文。此前调度节点记录按原日期保存。

日期：2026-11-20，Asia/Shanghai。

## 问题与范围

旧 Cron 使用 `floor(scheduledTime / 5分钟) % ceil(maxId / batchSize)` 决定 ID 段，没有持久进度。新增收录改变分母，可能跳过尚未刷新的段。构建媒体读取修复 PR #55 未修改这个调度公式。

本节点修复定时刷新调度，保留既有 D1/R2、5 分钟 Cron、每批上限和发布节流。用户要求对齐收录跳段问题；先提交独立 PR，不执行生产部署或初始化进度。原工作树用户修改保持不动。

## 实施与验收

1. 在现有 `site_state` 保存版本化进度 `refresh_progress_v1`：nextId、cycle、lastScheduledTime、lease；无需 migration 或新增 Cloudflare 资源。
2. 按下一条 ID 推进，maxId 增长或批大小变化不重算已有进度；预算不足、429 从第一条未处理记录继续。低活跃条目的隔轮刷新沿用，缺头像条目不因低活跃跳过。
3. 单键比较交换领取 20 分钟租约，完成后比较交换提交进度。重叠调用只有一个所有者；旧所有者不能覆盖新进度；已完成 tick 不重复推进。损坏状态失败关闭，不静默重置。
4. 首次运行只检查最新 ID 段，然后开始完整轮询。不把旧公式推测的位置写成历史完成记录。首轮尾段未处理完时不回绕。
5. 失败保留 dirty 发布意图、释放租约并保留进度；进程被终止时租约到期后重试。预留进度写入的子请求预算，保留日志 from/to/processed/deferred。
6. 验证新增收录、完整回绕、批大小变化、预算不足、429、R2 故障、重叠、过期接管、重复 tick、状态损坏；运行相关包类型检查及测试，PR CI 执行全仓检查。

## 上线与边界

- 生产部署另待用户授权，合并 PR 触发的网页构建不等于发布 bot Worker。部署前核验目标版本、现有进度键及最近刷新日志，不覆盖已有进度。
- 首次部署会在第一次成功领取时写入进度；不靠一次手工“校准”旧公式解决后续跳段。
- 失败会重试整段，D1/R2 副作用沿用既有幂等边界，不承诺跨存储事务。持久游标保证接续，不保证每个条目固定多久内更新；吞吐仍受每批大小、预算及限流影响。
- 回滚代码会恢复旧取模行为。保留进度键，重新部署修复版可接续；不删除生产状态来模拟恢复。
- 租约长度依据 [Workers Cron 15 分钟墙钟上限](https://developers.cloudflare.com/workers/platform/limits/#wall-time-limits-by-invocation-type)，检索于 2026-11-20。状态比较交换使用 D1 单条条件更新。
